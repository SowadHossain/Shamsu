
# SHAMSU Tech Stack Recommendations

Tech stacks chosen for maximum template reuse and minimum model burden. Each
stack prioritizes well-documented, commonly-seen patterns so a 7-8B model has
seen them in training data. Where a 7B model is weak (multi-file coordination,
novel architectures, complex state machines), that logic lives in the template,
not the model's fill-the-holes.

---

## 1. Multiplayer Games

### Stack

- Frontend: React + React-Three-Fiber + Three.js
- Networking: Colyseus (relay/room mode, NOT authoritative)
- Physics: Rapier (optional, included in template)
- Build: Vite + TypeScript
- Backend: None (relay server is pre-built boilerplate)

### Why this stack for small models

**React-Three-Fiber (R3F)**: Most well-documented WebGL abstraction. Tons of
examples online and in training data. Model can understand "hook up Rapier to
R3F and it works."

**Colyseus relay**: The game loop, netcode, room management, and relay message
passing are pre-built in the template. The model only writes: entity schemas, per-entity update functions, and game rules (win/lose). It never touches the
network or the message loop. This is why relay is better than authoritative for
a small model—authoritative requires correct server-side state mutation, which
is where 7B models break most.

**No backend**: The relay server is a stock Colyseus server, identical in every
game. It's in the template, not regenerated. Zero backend complexity for the
model to invent.

**TypeScript**: Enforces structure. The entity schema has types, function signatures
are checked, and type errors catch whole categories of bugs before testing. This
is huge for a small model.

### Model's actual job

Fill these holes (the manifest):

- `entity.player` — type definition for a player (position, rotation, health, etc.)
- `entity.obstacles` — obstacles/pickups (collider, position, type)
- `rule.update` — update all entities per tick (movement, collisions, spawning)
- `rule.win` — check for win/lose
- `ui.hud` — bind HUD state to game values

Template provides:

- Menu scene and lobby scene (HTML, CSS, state management)
- Relay room setup (connect, join, listen, send)
- Render loop (R3F camera, animation frame, Rapier integration)
- Player sync (broadcast position, receive remotes)
- Test helpers (headless join, inspect state)

### Effort estimate for model

- Holes: 5 small ones (3 schema, 2 function)
- Model context per hole: ~800 tokens (hole signature + a few examples)
- Token cost per hole: ~150-200 for generation + self-review
- Total: ~1000 tokens to fill all game logic (not including build/test loops)

## 2. Portfolio Sites

### Stack

- Frontend: SvelteKit (SSG, server-side rendering)
- Styling: TailwindCSS
- Content: Markdown + frontmatter (YAML) for metadata
- Build: Vite (included with SvelteKit)
- Backend: None

### Why this stack for small models

**SvelteKit**: Designed for simplicity. Less boilerplate than Next.js, smaller
mental model. Routes are just files. Layouts are just components. Compiler
catches errors at build time.

**Markdown content**: Text files, not databases. No model-generated SQL or
migrations. Content is completely static after build. Model cannot break a
database schema because there is no database.

**TailwindCSS**: Template-based styling. The model doesn't invent CSS; it uses
Tailwind class names. Classes are constrained (no arbitrary values), so the model
can't go off-road into broken CSS. Template has all layouts (hero, gallery, nav)
pre-built with `className` holes.

**No database**: Unlike multi-tenant or ecommerce, a portfolio is static after
build. This eliminates a whole category of model errors.

### Model's actual job

Fill these holes:

- `content.about` — markdown file about the person (optional, many portfolios don't customize)
- `content.projects` — array of project metadata (title, description, image, link)
- `ui.hero` — customize the hero section text and colors
- `ui.nav` — customize nav items and links
- `style.colors` — Tailwind color tokens for the portfolio theme

### Template provides

- Nav, footer, layout wrappers (complete)
- Project gallery grid (CSS complete, data-driven)
- Contact form (email service templated, model fills form fields)
- Responsive breakpoints (complete in CSS)
- Dark mode toggle (complete)

### Effort estimate

- Holes: 4-5 (mostly content fills, one or two component tweaks)
- Context per hole: ~500 tokens
- Token cost: ~100-150 per hole (simple fills, mostly strings)
- Total: ~700 tokens

## 3. Multi-Tenant Admin System

### Stack

- Frontend: Next.js + React + TypeScript
- UI components: shadcn/ui (Radix + Tailwind)
- Backend: Next.js API routes
- Database: PostgreSQL + Prisma ORM
- Auth: NextAuth.js (Auth.js)
- Build: Next.js (built-in)

### Why this stack for small models

**Next.js**: Industry standard, tons of examples, well-known patterns. Model
knows "pages/api/route.ts is a handler", "pages/dashboard is a page component",
routes are conventional.

**shadcn/ui**: Copy-paste components, not npm packages. The components live in
your repo as source code. Model can read them, understand them, and customize.
Not black-box npm. This matters because a 7B model needs to see the code to
modify it, and shadcn makes that the default.

**Prisma + PostgreSQL**: Prisma schema is readable and auto-migrated. Patterns for
multi-tenancy (every table has `tenantId`) are boilerplate in the template. Model
never writes migrations or raw SQL.

**NextAuth.js**: Auth is pre-built. The model doesn't invent auth logic. It only
customizes the login form or adds a custom provider config.

### Model's actual job

Fill these holes:

- `schema.entities` — add custom database entities (e.g., "teams have projects")
  to the Prisma schema (template already has `User`, `Tenant`, `Role`)
- `api.crud` — fill in the REST endpoints for a new entity (GET, POST, PUT, DELETE)
  using the templated CRUD pattern already in the codebase
- `ui.dashboard` — add a dashboard widget that displays aggregate data (chart,
  table, or stat card using shadcn components)
- `ui.form` — add a form for creating/editing a new entity
- `rbac.middleware` — define which roles can access which endpoint

### Template provides

- Auth flow (login, signup, session management)
- Role-based access control library (canAccess, requireRole middleware)
- Prisma multi-tenant queries (automatic tenantId filtering)
- REST CRUD generator (create, read, update, delete are the same pattern for all entities)
- Dashboard layout and shadcn component library
- Form component wrappers (validation, submission handlers)

### Effort estimate

- Holes: 5-7 (schema, 2-3 CRUD endpoints, 1-2 UI additions, RBAC rule)
- Context per hole: ~1200 tokens (schema examples, CRUD pattern, shadcn examples)
- Token cost: ~200-300 per hole (slightly more complex, needs to understand patterns)
- Total: ~1500-2000 tokens

## 4. E-Commerce Website

### Stack

- Frontend: Next.js + React + TypeScript
- UI: shadcn/ui (same as admin)
- Backend: Next.js API routes (minimal)
- Payments: Stripe (hosted checkout, not custom payment forms)
- Cart state: Zustand (simple, well-documented)
- Database: PostgreSQL + Prisma (optional, can use Stripe as source of truth)
- Build: Next.js

### Why this stack for small models

**Stripe Hosted Checkout**: Model never codes payment logic. Stripe is the source
of truth. Model only integrates: "redirect to checkout, listen for webhook."
This eliminates the largest source of bugs (payment code gone wrong = real
financial loss). The template has the webhook handler boilerplate.

**Next.js + shadcn**: Same as admin. Familiar, well-documented, copy-paste
components.

**Zustand for cart**: Simple state management. Model understands "set cart items"
without learning Redux or Context API internals. Template has the cart store
predefined; model customizes the cart page and checkout flow.

**Database optional**: Product catalog can be static (JSON/markdown in the repo)
or Prisma + PostgreSQL if you need inventory. Either way, the template
pre-builds the pattern, model just customizes data or queries.

### Model's actual job

Fill these holes:

- `content.products` — product database (JSON or Prisma data loading)
  or model fills JSON product data if static
- `ui.product_page` — customize the product detail page layout (images, reviews, variants)
- `ui.cart_page` — customize the cart display
- `ui.checkout_page` — customize checkout flow (address form, order summary)
- `api.stripe_webhook` — optional, if you need custom logic after payment
- `api.inventory` — optional, stock tracking (if database enabled)

### Template provides

- Stripe integration boilerplate (redirect, webhook, session tracking)
- Cart Zustand store (add, remove, update quantity)
- Product listing page template
- Cart and checkout pages (HTML/CSS/UX complete)
- Stripe API key management and environment variables
- Order confirmation page
- Simple inventory tracking (optional, included if database is enabled)

### Effort estimate

- Holes: 4-6 (product data, 1-2 UI customizations, maybe webhook if needed)
- Context per hole: ~1000 tokens
- Token cost: ~150-250 per hole
- Total: ~1000-1500 tokens

## 5. General/Standard Website (Fallback)

### Stack

- Frontend: SvelteKit (or Next.js if the site later needs a backend)
- Styling: TailwindCSS
- Content: Markdown + frontmatter (optional)
- Build: Vite (SvelteKit) or Next.js
- Backend: None (static, or minimal Next.js routes if needed)

### Why this stack

**SvelteKit**: When you don't know what the site is, SvelteKit is safe. It's
minimal, compiles cleanly, and works for static or dynamic. If the user later
says "actually add a backend," you can add API routes without refactoring.

**TailwindCSS + Markdown**: Safe defaults. No CSS to break, content is text.

### Model's actual job

Minimal constraints. The model adapts to what the user asks.

- Add pages (routes)
- Build forms
- Integrate APIs (if any)
- Style with Tailwind

### Template provides

- Nav and layout
- Basic routing
- Responsive grid and components
- Contact form boilerplate (or hook to send-email service)
- Dark mode (optional)

### Effort estimate

- Highly variable (could be 5 holes or 50 depending on the request)
- Use the smallest possible context per hole (one page per generation)
- Assume ~500 tokens per hole

## Key principles across all stacks

1. **No custom frameworks or DSLs**. Stick to industry standards.
2. **Type-safe languages** (TypeScript everywhere). Types catch bugs before testing.
3. **Component libraries, not custom components**. Use shadcn/ui, Headless UI,
   Radix. Don't ask the model to invent custom component APIs.
4. **Pre-built packages, not reinvention**. NextAuth, Stripe, Colyseus, Prisma
   are all templated, not regenerated. Model integrates, doesn't builds.
5. **Static content over databases when possible**. Markdown for portfolios,
   JSON for product catalogs. Model fills content, doesn't manage schema.
6. **API-first design**. Frontend and backend are separate concerns. Model can
   write a frontend that consumes a pre-built API, or a backend API that serves
   a pre-built frontend.
7. **Clear separation of model work vs template work**. If it's plumbing
   (routing, auth, state, network), it's in the template. If it's logic
   (rules, forms, views), the model fills it.

## Recommended build order for archetypes

Once you have the detection and DoD system working (per the Template Registry Plan):

1. **General/Web** — simplest, quickest to prove the registry works
2. **Portfolio Site** — next simplest, static only
3. **Multiplayer Game** — most complex, but most satisfying (proof that 7B can do hard things with a good template)
4. **E-Commerce** — medium, builds on Next+Tailwind knowledge from Game/Portfolio
5. **Multi-Tenant Admin** — last, builds on all the pattern knowledge from the others

This order lets you debug the system mechanics first (on easy stacks) before
tackling the harder stacks.
